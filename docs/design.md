# 工作原理、平台边界与后续方向

本页描述当前实现，不代表新的功能承诺。banhack233 组合 fail2ban / sshguard 风格防爆破、系统巡检、保活、通知和自启动；部分匹配思路相近，不等同于这些项目的完整兼容实现。

## 从日志到封禁

```text
启动：加载配置一次
  → 每轮加载状态
  → 释放到期或新白名单的已记录自动封禁（生产模式）
  → 按路径读取新增文本日志 / 查询 Windows 事件
  → 成功登录匹配：清空该规则下该 IP 的失败计数
  → 失败匹配：校验 IP → 跳过白名单 → 地区阈值 → 累计
  → 达到阈值：防火墙动作 / dry-run / notify 冷却
  → 写应用日志、发送或暂存通知
  → 到期时执行系统巡检
  → 保存状态，等待下一轮
```

成功登录只清除命中计数，不解除已存在封禁或通知冷却；它不会回溯撤销同一轮更早日志已经触发的动作。模式匹配按配置顺序选择一条匹配结果，同一日志行不会因为多个失败正则匹配而重复加分；一次认证产生多行失败日志仍可能多次累计。

`count_by_user=true` 且有用户名时，状态键为 `规则|IP|用户`；无用户名时为 `规则|IP`。两个人共用用户名仍共用计数。封禁动作只有来源 IP，没有客户端设备或 MAC 身份。

## 时间、状态与到期

- 失败窗口使用扫描到事件的时间。回放历史日志会把它们当成本轮观察事件；默认 `start_at_end=true` 用于避免首次全量回放。
- `ban_time` 由守护进程记录并在后续扫描释放；不是 nft 集合元素自带的到期倒计时。服务停止时不会继续自动解封。
- 同一个 IP 被多个规则/用户有效封禁时，防火墙条目保留到相关实际封禁都可释放。
- 解除失败保留状态，下轮重试。自定义动作不自动推测撤销命令。
- 状态持久化不等于防火墙持久化。主机重启或外部清空规则后，当前实现不会自动重建所有尚未到期的封禁；应核对实际规则和状态。
- `unban` 只处理防火墙，不清空计数和状态；删除状态文件也不会删除防火墙规则。
- 重命名/删除规则不会立即撤销旧规则留下的封禁；需要配合实际后端和到期状态处理。

## 文本日志读取边界

当前按“路径 + 字节偏移”跟踪日志，没有 inode/文件标识检查。文件变小会从头读取；轮转后新文件已经长于旧偏移时，可能遗漏开头。不要把这一机制理解成完整的日志轮转/投递保障。

多个规则共享同一 `log_paths` 会共享偏移，先读取的规则可能消耗后续规则需要的新增内容；将同一来源的匹配尽量合并到一条规则。两个文件若包含重复转发的同一认证事件，也可能重复累计。

Linux 当前没有原生 journald reader；Windows `eventlog:` 是单独实现，不支持把任意日志来源写成 URI。文本正则使用 Go regexp；不提供 PCRE lookaround/backreference，也不加载 fail2ban jail/filter 配置文件。

## 平台能力表

| 能力 | Linux | macOS | Windows |
| --- | --- | --- | --- |
| 二进制发布 | amd64 / arm64 | amd64 / arm64 | amd64 / arm64 |
| 自启动 | systemd | launchd | SYSTEM 计划任务 |
| 日志输入 | 文本文件 | 文本文件，需配置实际来源 | `OpenSSH/Operational` 事件或文本文件 |
| 自动防火墙 | nft 优先；没有 nft 命令时用 iptables/ip6tables | PF 表操作，需要现有匹配规则 | netsh 规则；当前端口方向问题见下文 |
| `secure-ssh` / `keepalive` | 支持 | 不支持 | 不支持 |
| 恶意程序扫描 | 轻量进程/持久化痕迹检查 | 报告不支持 | 报告不支持 |
| 地区识别 | IPv4 本地数据库 | 同左，需路径可用 | 同左，需路径可用 |

六平台构建成功不等于在六个平台完成真实阻断验收。Linux/Windows 的 CI 单元测试不替代目标主机防火墙与日志接入验证。

## 已知限制与部署影响

| 当前实现 | 对部署的影响 | 当前处理方式 |
| --- | --- | --- |
| Linux 自动规则固定 `tcp dport 22` | 自定义 SSH 端口不会跟随 sshd 的 `Port` 自动变化 | 使用 `action=notify` 或自行管理经过验证的动作；不要编造 `ssh_port` 字段 |
| nft 命令存在但运行失败时不继续试 iptables | 权限/内核支持问题会表现为扫描失败 | 看 `scan error` 和 nft 错误，修复实际后端 |
| Windows netsh 使用 `remoteport=22` | 入站匹配的是远端源端口，与常见 SSH 服务本地目标端口不同，通常不能实现预期 SSH 阻断 | 修复前不可依赖该自动规则保护 SSH；单独管理已验证的防火墙策略 |
| Windows 每轮查询最近 80 条事件，无事件游标/去重 | 同一失败可能被重复计数；事件顺序也不能当作文本顺序回放 | 自动封禁前先用观察/通知模式验收，事件去重是待修复项 |
| macOS 只操作 `banhack233` PF 表 | 没有自动安装引用该表的完整过滤规则；表中有地址不代表流量被阻断 | 由管理员配置并验收 PF 规则及 SSH 日志来源 |
| Windows 自启动状态不读取实时任务运行状态 | `active=false` 不能直接判定任务停止 | 用 `schtasks /Query /TN banhack233 /V /FO LIST` 核对 |
| macOS / 非管理员 Windows 安装路径可能与默认配置路径不同 | 未找到文件时退回默认值，容易看错配置 | 显式 `-config`，核对配置存在和平台字段 |
| SSH 审计只简读主配置文件 | 不完整解析 Include/Match/最终优先级，可能与有效值不同 | 用 `sshd -T` 和适用的连接上下文核对 |
| 通知串行、批次在内存，无持久重试 | 一条渠道失败影响后续渠道；进程中断可丢失待发消息 | 单渠道测试、保留本地日志；不要当作可靠消息总线 |

Windows 端口方向的判断依据是当前 [自动动作代码](../internal/ban/action.go) 与 [Microsoft netsh 参数说明](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/netsh-advfirewall)；这是一项源码确认的实现问题，不是本次已修复功能。

## 保活与安全边界

“24h SSH 保活”描述配置中的探测容忍窗口，不保证断网、主机休眠、服务重启或代理超时后仍维持原连接。密码/root 登录是受支持场景，`keepalive` 的登录策略仍需与主机实际要求一致。业务 TCP 长连接还需要自研 TCP 服务/客户端的 socket keepalive、协议心跳和合理的应用超时；只有显式 `-tcp` 才调整全局系统参数。

白名单意味着本程序跳过该来源的失败封禁；公司出口后面的恶意尝试也共享豁免。SSH 密钥/证书有助于身份管理，但当前程序不按密钥指纹做设备封禁。默认不按新连接频率丢弃连接，也不负责流量清洗、主机补丁安装或业务端口策略。

## 后续值得开发和验证的内容

以下均为后续候选，**尚未实现**；每项应有可复现验收，而非只增加功能说明。

| 优先级 | 方向 | 验收标准 |
| --- | --- | --- |
| 高 | Windows 本地目标端口修正、事件游标和去重 | 常见客户端源端口下阻断目标 SSH；同一事件只计一次，重启后不重放 |
| 高 | 可配置 SSH 端口及跨平台防火墙规则 | IPv4/IPv6、自定义端口、到期释放与真实连接验证 |

| 中 | 日志轮转、共享文件多规则、状态/防火墙一致性 | inode 更换无遗漏；多规则独立消费；重启后实际封禁可验证 |
| 中 | 通知超时、独立渠道失败和持久重试 | 一个失效 webhook 不阻塞扫描或其他渠道；可恢复待发事件 |
